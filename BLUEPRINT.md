## 1. Project Overview

### Vision
IMPYSERV (Importaciones y Servicios) es una empresa boliviana especialista en climatización, con más de 10 años de trayectoria, base en Santa Cruz de la Sierra y cobertura a todo Bolivia. El sitio web es la primera presencia digital formal de la marca. Sirve tres funciones: (1) generar agendamientos de visita técnica y contactos para proyectos grandes (hoteles/edificios), (2) mostrar un catálogo de equipos con precios visibles que el propio dueño (usuario único, no técnico) pueda mantener actualizado, y (3) construir confianza mediante un portafolio de proyectos reales (hospitales, hoteles, cooperativas).

### Goals
- Convertir visitas en agendamientos de visita técnica vía WhatsApp (objetivo #1).
- Generar contactos calificados para proyectos grandes B2B (objetivo #2).
- Permitir que el dueño administre el catálogo (agregar, quitar, editar precios y fotos) sin ayuda técnica.
- Transmitir seriedad técnica y experiencia mediante casos de éxito reales.

### Success Metrics
- Clics en botón WhatsApp / envíos de formulario "Agendar visita".
- Envíos de formulario de "Proyecto grande".
- Uso efectivo del panel admin (productos actualizados sin intervención de un desarrollador).
- Tiempo en página de Proyectos y profundidad de scroll en Inicio.

## 2. Tech Stack

| Layer | Technology | Why |
|-------|-----------|-----|
| Framework | Next.js 15 (App Router) | Necesitamos SSR/SEO para páginas públicas y rutas dinámicas server-rendered para el panel admin — Astro no es ideal aquí porque el admin requiere backend/auth reales, no solo islands. |
| Language | TypeScript (strict) | Seguridad de tipos en el modelo de datos del catálogo y los formularios. |
| Styling | Tailwind CSS v4 | Implementa rápido la paleta de marca definida en la Sección 7. |
| Components | shadcn/ui | Componentes de tabla/formulario listos para el panel admin, personalizables con Tailwind. |
| Database | Supabase (Postgres) | Una sola plataforma cubre base de datos + autenticación + almacenamiento de imágenes — la opción más simple dado el tamaño del proyecto (3 tablas, 1 usuario admin). |
| ORM | Ninguno — Supabase JS Client directo | Con solo 3 tablas pequeñas, añadir Prisma/Drizzle es sobre-ingeniería. Queries directas vía `@supabase/supabase-js` con tipos generados. |
| Auth | Supabase Auth (email/password) | Un solo usuario admin (el dueño). No se necesita registro público, OAuth social ni roles múltiples — el mínimo viable. |
| Storage de imágenes | Supabase Storage | Integrado con la misma plataforma; usado para fotos de productos y de proyectos. |
| Emails de leads | Resend | Notifica por correo cada vez que se envía el formulario de contacto/cotización. |
| Hosting | Vercel | Despliegue directo desde Next.js, cero configuración, dominio `impyserv.com` ya registrado se conecta por DNS. |
| Package Manager | npm | Consistente con el resto del entorno de trabajo del usuario. |

## 4. Data Model

### Entities

**`products`** (catálogo de equipos)
| Field | Type | Notes |
|-------|------|-------|
| id | uuid | PK, default `gen_random_uuid()` |
| name | text | ej. "Split LG 12000 BTU" |
| brand | text | LG, Samsung, otras |
| capacity_btu | integer | 9000 / 12000 / 18000 / 24000 / 36000 / 60000 |
| type | text | `split` \| `central` \| `vrf` |
| price | numeric(10,2) | en Bs. |
| image_url | text | URL de Supabase Storage |
| description | text | opcional, corto |
| active | boolean | default `true` — controla visibilidad pública |
| created_at / updated_at | timestamptz | default `now()` |

**`projects`** (casos de éxito / portafolio)
| Field | Type | Notes |
|-------|------|-------|
| id | uuid | PK |
| slug | text | único, para `/proyectos/[slug]` |
| client_name | text | ej. "Hotel Mito Andino" |
| location | text | ej. "Uyuni" |
| category | text | `salud` \| `hoteleria` \| `cooperativa` \| `edificio` |
| description | text | |
| image_url | text | |
| featured | boolean | destaca en Inicio |
| created_at | timestamptz | |

**`leads`** (formulario de contacto/cotización)
| Field | Type | Notes |
|-------|------|-------|
| id | uuid | PK |
| name | text | requerido |
| phone | text | requerido |
| city | text | |
| property_type | text | `casa` \| `oficina` \| `hotel_edificio` |
| service_type | text | `instalacion` \| `mantenimiento` \| `proyecto_grande` \| `cotizacion_equipo` |
| message | text | opcional |
| product_id | uuid | FK nullable → `products.id` (si vino desde el catálogo) |
| status | text | default `nuevo` — `nuevo` \| `contactado` \| `cerrado` |
| created_at | timestamptz | |

### Relationships
- `leads.product_id` → `products.id` (opcional, many-to-one): un lead puede originarse desde un producto específico del catálogo.
- `products` y `projects` no tienen relación directa entre sí.

### Database Schema
```sql
create table products (
  id uuid primary key default gen_random_uuid(),
  name text not null,
  brand text not null,
  capacity_btu integer not null,
  type text not null check (type in ('split', 'central', 'vrf')),
  price numeric(10,2) not null,
  image_url text,
  description text,
  active boolean not null default true,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table projects (
  id uuid primary key default gen_random_uuid(),
  slug text not null unique,
  client_name text not null,
  location text not null,
  category text not null check (category in ('salud', 'hoteleria', 'cooperativa', 'edificio')),
  description text not null,
  image_url text,
  featured boolean not null default false,
  created_at timestamptz not null default now()
);

create table leads (
  id uuid primary key default gen_random_uuid(),
  name text not null,
  phone text not null,
  city text,
  property_type text check (property_type in ('casa', 'oficina', 'hotel_edificio')),
  service_type text not null check (service_type in ('instalacion', 'mantenimiento', 'proyecto_grande', 'cotizacion_equipo')),
  message text,
  product_id uuid references products(id) on delete set null,
  status text not null default 'nuevo' check (status in ('nuevo', 'contactado', 'cerrado')),
  created_at timestamptz not null default now()
);

-- Row Level Security
alter table products enable row level security;
alter table projects enable row level security;
alter table leads enable row level security;

-- Público solo puede leer productos/proyectos activos
create policy "public_read_active_products" on products for select using (active = true);
create policy "public_read_projects" on projects for select using (true);

-- Solo usuarios autenticados (el admin) pueden escribir
create policy "admin_write_products" on products for all using (auth.role() = 'authenticated');
create policy "admin_write_projects" on projects for all using (auth.role() = 'authenticated');

-- Cualquiera puede crear un lead (formulario público), solo admin puede leer/actualizar
create policy "public_insert_leads" on leads for insert with check (true);
create policy "admin_read_leads" on leads for select using (auth.role() = 'authenticated');
create policy "admin_update_leads" on leads for update using (auth.role() = 'authenticated');
```

## 5. API Design

### Routes Overview
| Method | Path | Description | Auth |
|--------|------|-------------|------|
| POST | `/api/leads` | Recibe el formulario público de contacto/cotización, inserta en `leads`, dispara email vía Resend | No (público) |
| — | Server Action `createProduct` | Crea un producto en el catálogo | Sí (admin) |
| — | Server Action `updateProduct` | Edita nombre/precio/foto/estado de un producto | Sí (admin) |
| — | Server Action `deleteProduct` | Elimina un producto | Sí (admin) |
| — | Server Action `toggleProductActive` | Activa/desactiva sin borrar | Sí (admin) |
| — | Server Action `createProject` / `updateProject` | CRUD de casos de éxito (mismo patrón que productos) | Sí (admin) |

**Decisión de diseño:** las mutaciones del panel admin usan **Server Actions** de Next.js en vez de rutas REST separadas — es el patrón más simple para un panel CRUD de un solo usuario, evita duplicar validación cliente/servidor en dos capas. Solo el formulario público (`/api/leads`) usa un Route Handler porque necesita ser un endpoint estable llamable desde un componente cliente con `fetch`.

### Key Endpoints Detail

**`POST /api/leads`**
- Body: `{ name, phone, city?, property_type, service_type, message?, product_id? }`
- Validación: esquema Zod (`lib/validations/lead.ts`), rechaza si falta `name`, `phone` o `service_type`.
- Response 201: `{ success: true }`
- Response 400: `{ success: false, errors: {...} }`
- Efecto secundario: envía correo a `alfonsoespoz@impyserv.com` vía Resend con los datos del lead.

**Server Action `createProduct` / `updateProduct`**
- Input validado con el mismo esquema Zod (`lib/validations/product.ts`) usado en el formulario del panel.
- Sube la imagen a Supabase Storage (bucket `products`) antes de insertar/actualizar la fila.
- Revalida la ruta `/catalogo` (`revalidatePath`) para que el cambio se vea de inmediato en el sitio público.

### State Management
- **Server Components por defecto** para todas las páginas públicas (fetch directo a Supabase en el servidor, sin loading spinners innecesarios).
- **Client Components** solo donde hay interactividad: `ProductFilters`, `QuoteForm`, `ProductForm` (admin).
- No se necesita estado global (Redux/Zustand) — el alcance del sitio no lo justifica. Cache/revalidación se maneja con `revalidatePath` de Next.js tras cada mutación admin.

## 8. Authentication & Authorization

### Auth Flow
Un único usuario administrador (el dueño, `alfonsoespoz@impyserv.com`) creado manualmente desde el dashboard de Supabase — **no hay registro público**. Login en `/admin/login` con email/password vía Supabase Auth. Al autenticarse, cookie de sesión gestionada por `@supabase/ssr`.

### Protected Routes
- `/admin/**` — requiere sesión válida. `middleware.ts` verifica la sesión en cada request; si no existe, redirige a `/admin/login`.
- Todas las demás rutas son públicas.

### Roles & Permissions
| Role | Can Do |
|------|--------|
| `admin` (único usuario) | Crear, editar, activar/desactivar y borrar productos y proyectos; ver y actualizar el estado de los leads |
| Público (no autenticado) | Ver páginas públicas, catálogo activo, proyectos, enviar formulario de contacto |

No se necesitan roles adicionales — un solo usuario cubre el caso de uso completo.

### Session Management
Cookie-based, httpOnly, gestionada automáticamente por `@supabase/ssr` (refresco de sesión en el middleware en cada request).

`npx create-next-app@latest impyserv --typescript --tailwind --app --src-dir` → configurar ESLint/Prettier → instalar `@supabase/supabase-js @supabase/ssr resend react-hook-form zod @hookform/resolvers lucide-react`.

`Header`, `Footer`, `WhatsAppButton` flotante, `layout.tsx` raíz con metadata SEO base y fuentes (Poppins + Inter vía `next/font`).

**Step 5: Home**
Construir `page.tsx` de Inicio sección por sección: Hero → TrustBar → ServicesGrid → FeaturedProjects → FeaturedCatalog → WhyUs → CTASection, con los textos de la Sección 11 del blueprint original ya redactados.

**Step 6: Páginas de Servicios**
`/servicios`, `/servicios/mantenimiento`, `/servicios/instalacion`, `/servicios/proyectos-grandes` — contenido estático server-rendered.

**Step 7: Catálogo Público**
`lib/supabase/server.ts` (cliente de servidor) → `/catalogo` con `ProductGrid` + `ProductFilters` (Client Component) → fetch de productos activos.

**Step 8: Formulario de Leads**
`QuoteForm` reutilizable (React Hook Form + Zod) → `/api/leads/route.ts` → integración con Resend para notificación por correo. Insertar el formulario en Home, Catálogo (precargado con producto) y `/contacto`.

**Step 9: Proyectos (Portafolio)**

**Step 10: Nosotros y Contacto**
Páginas estáticas con la historia, +10 años, flotilla, cobertura nacional; `/contacto` con formulario completo + datos (WhatsApp 77085250, correo, horario, redes).

**Step 11: Auth del Panel Admin**
`middleware.ts` protegiendo `/admin/**` → `/admin/login` con Supabase Auth → `admin/layout.tsx` validando sesión server-side.

**Step 12: Panel de Catálogo (CRUD)**
`ProductTable` (listar todos, incluidos inactivos) → `ProductForm` (crear/editar, con subida de imagen a Storage) → Server Actions `createProduct`, `updateProduct`, `deleteProduct`, `toggleProductActive` → `revalidatePath('/catalogo')` tras cada mutación.

**Step 13: SEO**
Metadata (`title`/`description`) por página, `sitemap.xml` vía `app/sitemap.ts`, Open Graph image, datos estructurados JSON-LD tipo `LocalBusiness`.

**Step 14: Testing (smoke)**
Playwright: todas las páginas públicas cargan, el formulario envía y aparece en `leads`, el login admin funciona, el admin puede crear/editar/desactivar un producto y el cambio se refleja en `/catalogo`.

**Step 15: Deploy**
Conectar repo a Vercel → configurar variables de entorno (Sección 10) → conectar dominio `impyserv.com` vía DNS → verificar en producción.

## 12. Deployment Strategy

### Hosting
Vercel, conectado directamente al repositorio Git. Zero-config para Next.js.

### CI/CD
Patrón mínimo (adecuado para este tamaño de proyecto): push a `main` → deploy automático a producción. Pull requests → preview deploy automático (funciona como staging).

### Domain & DNS
`impyserv.com` ya está registrado. En Vercel: Project → Domains → agregar `impyserv.com` → configurar el registro DNS (A o CNAME) que Vercel indique en el proveedor del dominio.

### Environments

## 13. Testing Strategy

### Unit Tests
No es prioritario dado el tamaño del proyecto — el valor está en la validación de esquemas Zod, que ya actúa como capa de corrección para los formularios.

### Integration Tests
Verificar manualmente (o con un test simple) que las Server Actions del panel admin respetan las políticas RLS: un usuario no autenticado no puede mutar `products`/`projects`, pero sí puede insertar en `leads`.

### E2E Tests (Playwright)
Flujos críticos a cubrir antes de cada deploy a producción:
1. Todas las páginas públicas cargan sin error (`/`, `/servicios/*`, `/catalogo`, `/proyectos`, `/nosotros`, `/contacto`).
2. El formulario de cotización se envía correctamente y aparece en `leads`.
3. El botón de WhatsApp abre con el número y mensaje correctos.
4. Login de admin funciona; acceso a `/admin/catalogo` sin sesión redirige a `/admin/login`.
5. El admin puede crear, editar, desactivar y borrar un producto, y el catálogo público refleja el cambio.

## 16. Reglas No Negociables

1. **TypeScript estricto, sin `any`.** El modelo de datos del catálogo y los formularios deben estar completamente tipados.
2. **RLS obligatorio en toda tabla de Supabase.** Público solo lee `products` activos y `projects`; solo el usuario autenticado (admin) puede escribir.
3. **La clave `SUPABASE_SERVICE_ROLE_KEY` nunca se expone al cliente** — uso exclusivo en Server Actions/Route Handlers.
4. **Nunca commitear `.env.local`.** Usar `.env.example` con placeholders.
5. **Mobile-first en todas las páginas.** El botón de WhatsApp flotante debe estar siempre visible en scroll.
6. **Un componente por archivo, máximo 300 líneas.**
7. **Todo formulario público (`QuoteForm`) y de admin (`ProductForm`) se valida con el mismo esquema Zod en cliente y servidor** — nunca confiar solo en validación del lado del cliente.
8. **Precios siempre visibles y en Bs.**, formateados de forma consistente en todo el sitio.
9. **Cada mutación del panel admin (crear/editar/borrar producto) debe llamar `revalidatePath('/catalogo')`** para que el catálogo público se actualice sin caché obsoleta.
10. **Cada página pública debe tener `title` y `meta description` propios** (SEO) — no usar metadata genérica heredada del layout raíz.
